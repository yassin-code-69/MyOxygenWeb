## Parallel Execution Strategy

The plans have been decoupled to allow parallel subagent execution while respecting critical architectural dependencies:

```
                  ┌───► [Plan 005: Design System & Primitives (frontend)] ───┐
                  │                                                          │
                  │                                                          ▼
                  │                                    [Plan 006: Storefront Pages (frontend)]
                  │                                                          │
                  │                                                          ▼
[Phase 1-4 Done] ─┼───► [Plan 007: Purchase Funnel & Checkout (backend + frontend)]
                  │                         │                               │
                  │                         ▼                               ▼
                  ├───► [Plan 008: Courier & Invoices (backend)]    [Plan 009: Admin Portal]
                  │                         │                               │
                  │                         └───────────────┬───────────────┘
                  │                                         ▼
                  └───► [Plan 010: Concurrency Race Tests & Docker Packaging]
```

1. **Sprint A (Parallel Execution)**:
   - **Agent 1 (Frontend UI Specialist)**: Execute **Plan 005** (`frontend/`).
   - **Agent 2 (Order & Funnel Specialist)**: Execute **Plan 007 Backend** (`backend/` order schema, coupon validation, checkout route, FEFO reservation).
2. **Sprint B (Parallel Execution)**:
   - **Agent 1 (Frontend Storefront Specialist)**: Execute **Plan 006** (Catalog Explorer & Product Detail Page) and **Plan 007 Frontend** (Cart Drawer, Zustand store, Multi-Step Checkout Stepper).
   - **Agent 2 (Logistics & Operations Specialist)**: Execute **Plan 008** (`backend/` Steadfast Courier adapter, `pdf-lib` invoice generator, email/SMS notification hub).
3. **Sprint C (Parallel Execution with 6 Specialized Subagents > 4 agents)**:
   - **Agent 1 (Admin Orders & Telemetry Backend Specialist)**: `GET /admin/analytics/summary`, `GET /admin/orders`, `PATCH /admin/orders/:id/status` (restores inventory on cancellation), `POST /admin/orders/:id/dispatch-courier` in `backend/`.
   - **Agent 2 (Admin Batch Inspector & Ledger Backend Specialist)**: `GET /admin/batches` (expiry alerts: `EXPIRED`, `EXPIRING_SOON`, `HEALTHY`), `GET /admin/inventory/ledger` (paginated audit log) in `backend/`.
   - **Agent 3 (Admin Shell & Dashboard UI Specialist)**: Admin sidebar navigation layout, telemetry metric cards (Revenue, Orders, Low Stock, Expiring Soon), recent orders in `frontend/app/admin/`.
   - **Agent 4 (Admin Orders & Logistics UI Specialist)**: Order fulfillment table, status transition dropdown, Steadfast parcel booking modal, invoice download in `frontend/app/admin/orders/`.
   - **Agent 5 (Admin Batch Inspector & Ledger UI Specialist)**: Batch inspector table with color-coded shelf-life warnings and batch import modal, stock audit ledger table in `frontend/app/admin/batches/` and `frontend/app/admin/ledger/`.
   - **Agent 6 (Concurrency Hardening & Docker DevOps Specialist)**: 10 concurrent requests FEFO race condition stress test, `/health` deep diagnostics, multi-stage Dockerfiles (`backend/Dockerfile`, `frontend/Dockerfile`), and `docker-compose.yml`.

## Repository Invariants & Rules

1. **Independent 3-Folder Layout**:
   - `backend/` (Bun + Hono.js + Drizzle ORM on Supabase PostgreSQL)
   - `frontend/` (Next.js 16 + Mantine 9 Storefront)
   - `context/` (Architecture rules & specifications)
   - **NEVER** introduce `pnpm-workspace.yaml`, Turborepo, or shared `packages/`.
2. **Single-Owner Model**:
   - Strictly single-owner retail e-commerce. Reject any multi-vendor or merchant registration logic.
3. **Design Tokens**:
   - Primary Pink `#FF6B8B`, Secondary Green `#4CAF7D`, Accent Purple `#A78BFA`, Cream BG `#FFF8F6`, Surface White `#FFFFFF`. Currency: Bangladeshi Taka `৳`.
4. **FEFO Inventory & Batch Tracking**:
   - Stock allocations must always satisfy First-Expired, First-Out (`expiry_date ASC`) inside an atomic database transaction.
